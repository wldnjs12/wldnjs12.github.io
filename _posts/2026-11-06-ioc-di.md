## 👋 `new`는 누가 대신 해줬을까?
지금까지 이런 코드를 아무렇지 않게 써 왔습니다.

```java
@Service
@RequiredArgsConstructor
public class MemberService {
    private final MemberRepository memberRepository;
}
```

`MemberService`도, `MemberRepository`도 우리는 **한 번도 `new`로 만든 적이 없습니다.** 그런데 실행해 보면 `memberRepository`에는 멀쩡한 객체가 들어 있어요. 심지어 4편에서는 진짜 객체 대신 **프록시**가 들어간다고까지 했죠.

이번 글에서는 이 마법의 정체, 스프링의 뿌리인 **IoC(제어의 역전)** 와 **DI(의존성 주입)** 를 정리합니다.

---

## 😵 1. 스프링 없이 직접 조립하면?
회원 서비스를 순수 자바로 만든다고 해 볼게요.

```java
public class MemberService {
    private final MemberRepository memberRepository = new JdbcMemberRepository();

    public void join(Member member) {
        memberRepository.save(member);
    }
}
```

잘 동작합니다. 그런데 DB 접근 기술을 JDBC에서 JPA로 바꾸기로 했다면?

```java
public class MemberService {
    // private final MemberRepository memberRepository = new JdbcMemberRepository();
    private final MemberRepository memberRepository = new JpaMemberRepository();
}
```

### 🚫 무엇이 문제일까?
1. **코드를 고쳐야 한다:** 인터페이스(`MemberRepository`)에 의존하도록 잘 만들었는데도, `new JdbcMemberRepository()`라는 **구현체 이름이 박혀 있어서** Service 코드를 직접 수정해야 합니다.
2. **여러 곳에 퍼져 있다:** `MemberRepository`를 쓰는 클래스가 10개면 10곳을 다 고쳐야 합니다.
3. **테스트가 어렵다:** 테스트에서 가짜(Mock) 저장소로 바꿔 끼우고 싶어도, 내부에서 직접 `new` 하고 있으니 바꿀 방법이 없어요.
4. **객체가 계속 새로 생긴다:** 요청마다 `new MemberService()`를 하면 똑같은 역할의 객체가 끝없이 생겼다 사라집니다.

> 핵심 문제는 **"사용하는 쪽이 무엇을 쓸지 직접 고르고 만든다"** 는 것입니다. 객체지향 설계 원칙으로 말하면 **OCP(확장엔 열려 있고 변경엔 닫혀 있어야 함)** 와 **DIP(구체가 아닌 추상에 의존해야 함)** 를 어기고 있어요.
{: .prompt-warning }

## 🔄 2. IoC: 제어의 역전
해결책은 단순합니다. **Service가 직접 만들지 말고, 밖에서 넣어 주게 하자.**

```java
public class MemberService {
    private final MemberRepository memberRepository;

    // 무엇이 들어올지 MemberService는 모른다
    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```

그리고 조립은 **별도의 설정 담당**이 맡습니다.

```java
public class AppConfig {
    public MemberRepository memberRepository() {
        return new JpaMemberRepository();   // 바꿀 곳은 여기 한 줄뿐
    }

    public MemberService memberService() {
        return new MemberService(memberRepository());
    }
}
```

이제 `MemberService`는 **자기가 어떤 구현체와 일하는지 모릅니다.** 그냥 받은 걸 쓸 뿐이에요.

* **이전:** 내가 필요한 객체를 **내가 직접** 만들고 고른다.
* **이후:** 필요한 객체를 **외부가** 만들어서 넣어 준다.

이렇게 **프로그램의 제어 흐름(객체 생성·연결)을 내가 아닌 외부가 쥐는 것**을 **IoC(Inversion of Control, 제어의 역전)** 라고 합니다.

식당으로 치면 **주방장과 식자재 납품**입니다. 주방장(Service)이 매일 시장에 가서 재료를 직접 고르는 게 아니라, 구매 담당(AppConfig)이 정해 준 납품업체에서 재료가 **알아서 들어옵니다.** 납품업체가 바뀌어도 주방장의 요리법은 그대로예요.

> **프레임워크 vs 라이브러리**도 이 차이로 구분합니다. 내가 호출하면 **라이브러리**, 프레임워크가 내 코드를 호출하면 **프레임워크**입니다. 우리는 Controller를 만들기만 했고 호출은 DispatcherServlet이 했죠(1편). 스프링이 프레임워크인 이유입니다.
{: .prompt-info }

## 💉 3. DI: 의존성 주입
IoC가 "제어를 넘긴다"는 **원칙**이라면, **DI(Dependency Injection, 의존성 주입)** 는 그걸 구현하는 **구체적인 방법**입니다. 의존하는 객체를 **외부에서 주입**해 주는 것이죠.

위 예제에서 `AppConfig`가 `MemberService` 생성자에 `JpaMemberRepository`를 넣어 준 것이 바로 DI입니다.

* **정적인 의존관계:** 코드만 봐도 알 수 있는 관계 → `MemberService`는 `MemberRepository` **인터페이스**에 의존
* **동적인 의존관계:** 실행해 봐야 아는 관계 → 실제로 들어온 건 `JpaMemberRepository` **인스턴스**

DI 덕분에 **코드(정적 관계)는 건드리지 않고 실행 시점의 구현체(동적 관계)만 바꿀 수 있습니다.** 테스트할 때 가짜 저장소를 넣는 것도 이제 쉬워요.

```java
@Test
void join() {
    MemberService memberService = new MemberService(new FakeMemberRepository());
    // ...
}
```

## 📦 4. 스프링 컨테이너와 스프링 빈 ⭐⭐가장 중요
그런데 `AppConfig` 같은 조립 코드를 매번 직접 만들긴 번거롭습니다. **스프링이 이 역할을 대신 해 주는데**, 그게 바로 **스프링 컨테이너**입니다.

* **스프링 컨테이너(`ApplicationContext`):** 객체를 생성하고, 의존관계를 연결하고, 생명주기를 관리하는 **거대한 조립 공장 + 보관소**
* **스프링 빈(Bean):** 스프링 컨테이너가 만들고 관리하는 객체

### 빈을 등록하는 두 가지 방법

**① `@Configuration` + `@Bean`: 직접 등록**
```java
@Configuration
public class AppConfig {

    @Bean
    public MemberRepository memberRepository() {
        return new JpaMemberRepository();
    }

    @Bean
    public MemberService memberService() {
        return new MemberService(memberRepository());
    }
}
```
외부 라이브러리 객체처럼 **내가 클래스에 어노테이션을 붙일 수 없는 경우**에 주로 씁니다.

**② 컴포넌트 스캔: 자동 등록**
```java
@Service
public class MemberService { ... }
```
`@Component`가 붙은 클래스를 스프링이 **알아서 찾아서** 빈으로 등록합니다. 우리가 써 온 어노테이션들은 사실 모두 `@Component`를 품고 있어요.

| 어노테이션 | 쓰는 곳 | 추가 기능 |
| --- | --- | --- |
| `@Component` | 일반 컴포넌트 | - |
| `@Controller` / `@RestController` | 웹 계층 | 스프링 MVC 컨트롤러로 인식 |
| `@Service` | 비즈니스 계층 | 특별한 기능 없음 (역할 표시용) |
| `@Repository` | 데이터 접근 계층 | DB 예외를 스프링 예외로 변환 |
| `@Configuration` | 설정 클래스 | `@Bean` 싱글톤 보장 |

> **스캔 범위:** `@SpringBootApplication` 안에 `@ComponentScan`이 들어 있고, **이 클래스가 있는 패키지와 그 하위 패키지**를 스캔합니다. 그래서 메인 클래스는 보통 **최상위 패키지**에 둡니다. 다른 패키지에 만든 클래스가 "빈을 찾을 수 없다"고 나온다면 위치부터 확인하세요.
{: .prompt-tip }

### 컨테이너가 하는 일
```text
애플리케이션 시작
  → 컴포넌트 스캔 / @Bean 메서드로 등록할 빈 목록 파악
  → 빈 객체 생성
  → 의존관계 주입 (생성자에 필요한 빈을 찾아 연결)
  → @Transactional 같은 게 붙어 있으면 프록시로 감싸서 대신 등록 (4편)
  → 준비 완료! 요청이 오면 DispatcherServlet이 Controller 빈을 호출 (1편)
```

4편의 의문이 여기서 풀립니다. **Controller가 진짜 `AccountService` 대신 프록시를 받을 수 있었던 건**, Controller가 직접 `new` 하지 않고 **컨테이너가 주는 걸 받기만 했기 때문**이에요. 컨테이너가 프록시를 건네주면 Controller는 그게 프록시인지도 모릅니다. DI가 없었다면 AOP도 불가능했습니다.

## 🧩 5. 의존성 주입 방법 3가지
컨테이너가 빈을 넣어 주는 방법은 크게 세 가지입니다.

### ① 필드 주입
```java
@Service
public class MemberService {
    @Autowired
    private MemberRepository memberRepository;
}
```
가장 짧지만 **권장하지 않습니다.** 스프링 컨테이너 없이는 값을 넣을 방법이 없어서 순수 단위 테스트가 어렵고, `final`도 쓸 수 없어요.

### ② 수정자(Setter) 주입
```java
@Service
public class MemberService {
    private MemberRepository memberRepository;

    @Autowired
    public void setMemberRepository(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```
**선택적이거나 실행 중에 바뀔 수 있는** 의존관계에만 씁니다. 누구나 setter를 호출해 바꿀 수 있다는 게 단점이에요.

### ③ 생성자 주입 ✅ 권장
```java
@Service
public class MemberService {
    private final MemberRepository memberRepository;

    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```
* **불변:** `final`로 선언해 한 번 주입되면 바뀌지 않습니다.
* **누락 방지:** 의존성을 빼먹으면 **컴파일 단계에서** 바로 알 수 있습니다.
* **테스트 용이:** 스프링 없이 `new MemberService(가짜)`로 바로 테스트할 수 있어요.
* **순환 참조 조기 발견:** A가 B를, B가 A를 필요로 하면 **애플리케이션 시작 시점에** 에러로 알려줍니다.
* 생성자가 **하나뿐이면 `@Autowired`를 생략**할 수 있습니다.

### 그래서 `@RequiredArgsConstructor`
Lombok의 `@RequiredArgsConstructor`는 **`final` 필드를 모아 생성자를 자동으로 만들어 줍니다.** 즉 우리가 써 온 코드는 생성자 주입 그 자체였어요.

```java
@Service
@RequiredArgsConstructor   // 위의 생성자를 컴파일 시점에 만들어 줌
public class MemberService {
    private final MemberRepository memberRepository;
}
```

> 정리하면 **`private final` + `@RequiredArgsConstructor`** 조합이 사실상 표준입니다. `final`을 깜빡하면 생성자에 포함되지 않아 주입이 안 되니(`null`) 주의하세요.
{: .prompt-tip }

## ♻️ 6. 스프링 빈은 싱글톤
스프링 컨테이너는 기본적으로 **빈을 딱 하나만 만들어서** 모든 곳에 같은 객체를 나눠 줍니다. 이를 **싱글톤 스코프**라고 해요.

요청이 초당 1,000번 들어와도 `MemberService` 객체는 **하나**입니다. 요청마다 `new` 하던 1장의 문제(객체 낭비)가 해결되죠.

### ⚠️ 그래서 상태를 가지면 안 된다
객체 하나를 **여러 요청(스레드)이 동시에** 쓰기 때문에, 빈에 값을 저장하는 필드가 있으면 큰일이 납니다.

```java
@Service
public class OrderService {
    private int price;   // ❌ 모든 요청이 공유하는 필드

    public void order(String name, int price) {
        this.price = price;   // A 요청이 10,000원 저장
                              // 그 사이 B 요청이 20,000원으로 덮어씀
    }

    public int getPrice() {
        return price;         // A는 20,000원을 받게 된다!
    }
}
```

```java
@Service
public class OrderService {
    public int order(String name, int price) {
        return price;   // ✅ 지역 변수/파라미터/반환값으로 처리
    }
}
```

> **스프링 빈은 무상태(stateless)로 설계하세요.** 필드에는 `final`로 주입받은 다른 빈(Repository 등)처럼 **변하지 않는 것만** 두고, 요청마다 달라지는 값은 **지역 변수·파라미터·반환값**으로 다룹니다. 그리고 데이터는 DB에 저장하면 됩니다.
{: .prompt-warning }

## 🔀 7. 같은 타입의 빈이 여러 개라면?
`MemberRepository` 구현체가 두 개 다 빈으로 등록돼 있다면, 스프링은 어느 걸 넣어야 할지 몰라 `NoUniqueBeanDefinitionException`을 던집니다.

```java
@Repository
public class JpaMemberRepository implements MemberRepository { ... }

@Repository
public class MemoryMemberRepository implements MemberRepository { ... }
```

해결 방법은 두 가지입니다.

```java
// ① @Primary: 기본으로 쓸 빈 지정
@Primary
@Repository
public class JpaMemberRepository implements MemberRepository { ... }
```

```java
// ② @Qualifier: 주입받는 쪽에서 이름으로 지정
public MemberService(@Qualifier("memoryMemberRepository") MemberRepository memberRepository) {
    this.memberRepository = memberRepository;
}
```

* **`@Primary`**: "특별한 말이 없으면 이걸 써라" — 주로 쓰는 메인 구현체에
* **`@Qualifier`**: "여기서는 꼭 이걸 써라" — 가끔 쓰는 특수 구현체에
* 둘 다 있으면 더 구체적인 **`@Qualifier`가 우선**합니다.

> 참고로 `List<MemberRepository>`나 `Map<String, MemberRepository>`로 받으면 **해당 타입의 빈을 전부** 주입받을 수도 있습니다. 할인 정책처럼 여러 전략 중 하나를 골라 쓰는 경우에 유용해요.
{: .prompt-info }

## 🧭 8. 한 장으로 정리
| 개념 | 한 줄 정리 |
| --- | --- |
| IoC | 객체 생성·연결의 **제어권을 외부(컨테이너)에 넘기는 것** |
| DI | 필요한 객체를 **외부에서 주입**받는 IoC의 구현 방법 |
| 스프링 컨테이너 | 빈을 생성·연결·관리하는 `ApplicationContext` |
| 스프링 빈 | 컨테이너가 관리하는 객체, 기본은 **싱글톤** |
| 빈 등록 | 내 클래스는 **컴포넌트 스캔**, 외부 라이브러리는 **`@Bean`** |
| 주입 방법 | **생성자 주입** (`private final` + `@RequiredArgsConstructor`) |
| 빈 설계 | **무상태**로, 요청별 값은 지역 변수로 |
| 같은 타입 여러 개 | **`@Primary`** (기본) / **`@Qualifier`** (지정) |
