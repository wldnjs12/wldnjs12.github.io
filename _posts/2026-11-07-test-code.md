## 👋 "잘 되는 것 같은데요?"는 증명이 아니다
지난 글에서 생성자 주입의 장점으로 **"테스트하기 쉽다"** 를 여러 번 말했습니다. 그런데 정작 우리는 지금까지 어떻게 확인해 왔을까요?

서버를 띄우고, Postman으로 요청을 보내고, 응답을 눈으로 확인하고, DB를 열어서 값이 들어갔는지 봤습니다. 이번 글에서는 이 과정을 **코드로 자동화**하는 방법, **테스트 코드**를 정리합니다.

---

## 😵 1. 손으로 테스트하면 생기는 일
5편에서 만든 `ErrorCode`에 새 에러를 추가하면서 `GlobalExceptionHandler`를 살짝 고쳤다고 해 볼게요. 무엇을 다시 확인해야 할까요?

* 회원 조회 404는 여전히 잘 나오나?
* `@Valid` 검증 실패 400은?
* 잔액 부족은? 이체 롤백은?

### 🚫 무엇이 문제일까?
1. **느리다:** 서버 기동 → 요청 → 확인을 기능마다 반복해야 합니다.
2. **빠뜨린다:** 고친 곳만 확인하고, **멀쩡하던 다른 기능이 깨진 것**(회귀 버그)은 놓치기 쉽습니다.
3. **남지 않는다:** "어제 확인했어요"는 기록이 아닙니다. 다른 사람이 같은 확인을 반복할 수 없어요.

테스트 코드가 있으면 **버튼 한 번(`./gradlew test`)에 수백 개의 확인이 몇 초 만에** 끝납니다. 그래서 코드를 고치는 게 두렵지 않게 되죠.

> 식당으로 치면 **레시피 검수표**입니다. 새 메뉴를 추가할 때마다 "기존 메뉴 맛이 그대로인가"를 주방장 감으로 확인하는 게 아니라, 정해진 체크리스트로 매번 똑같이 검사하는 거예요.
{: .prompt-info }

## 🧪 2. JUnit5 기본: 테스트의 뼈대
Spring Boot 프로젝트에는 `spring-boot-starter-test`가 기본으로 들어 있고, 여기에 **JUnit5, AssertJ, Mockito**가 모두 포함되어 있습니다. 테스트 코드는 `src/test/java` 아래에 둡니다.

```java
class CalculatorTest {

    @Test
    @DisplayName("두 수를 더한다")
    void add() {
        // given
        Calculator calculator = new Calculator();

        // when
        int result = calculator.add(2, 3);

        // then
        assertThat(result).isEqualTo(5);
    }
}
```

* **`@Test`**: 이 메서드가 테스트임을 표시
* **`@DisplayName`**: 테스트 결과에 보일 이름 (한글로 의도를 적기 좋아요)
* **`@BeforeEach` / `@AfterEach`**: 각 테스트 **전/후**에 매번 실행
* **`@BeforeAll` / `@AfterAll`**: 전체 테스트 **전/후**에 한 번 실행 (`static` 메서드)

### given / when / then
테스트는 보통 세 단락으로 나눠 씁니다.
* **given:** 이런 상황이 주어졌을 때 (준비)
* **when:** 이걸 실행하면 (실행)
* **then:** 이런 결과가 나와야 한다 (검증)

이 틀만 지켜도 **"이 테스트가 뭘 확인하는지"** 가 한눈에 보입니다.

---

## ✅ 3. AssertJ: 읽히는 검증
검증은 JUnit 기본 `assertEquals`보다 **AssertJ의 `assertThat`** 을 주로 씁니다. 메서드를 체인으로 이어서 **문장처럼 읽히거든요.**

```java
assertThat(member.getName()).isEqualTo("홍길동");
assertThat(members).hasSize(3)
                   .extracting("name")
                   .contains("홍길동", "김철수");
assertThat(account.getBalance()).isPositive();
```

예외가 **발생해야 하는** 상황도 검증할 수 있습니다.

```java
assertThatThrownBy(() -> account.withdraw(20_000))
        .isInstanceOf(BusinessException.class)
        .hasMessage("잔액이 부족합니다.");
```

> `assertEquals(expected, actual)`는 **인자 순서를 헷갈리기 쉬워서** 실패 메시지가 거꾸로 나오곤 합니다. `assertThat(actual).isEqualTo(expected)`는 그럴 일이 없어요.
{: .prompt-tip }

## ⚡ 4. 단위 테스트: 스프링 없이 빠르게
**단위 테스트**는 클래스 하나(또는 메서드 하나)를 **다른 것과 떼어내서** 검증합니다. 스프링 컨테이너를 띄우지 않으니 **밀리초 단위**로 끝나요.

### ① 도메인 로직 테스트
5편에서 `Account` 엔티티 안에 넣은 출금 로직은 순수 자바 코드라서 그대로 테스트할 수 있습니다.

```java
class AccountTest {

    @Test
    @DisplayName("잔액보다 많이 출금하면 예외가 발생한다")
    void withdraw_fail() {
        // given
        Account account = new Account(10_000L);

        // when & then
        assertThatThrownBy(() -> account.withdraw(20_000L))
                .isInstanceOf(BusinessException.class)
                .hasMessage(ErrorCode.INSUFFICIENT_BALANCE.getMessage());
    }

    @Test
    @DisplayName("출금하면 잔액이 줄어든다")
    void withdraw_success() {
        Account account = new Account(10_000L);

        account.withdraw(3_000L);

        assertThat(account.getBalance()).isEqualTo(7_000L);
    }
}
```

> **비즈니스 로직을 엔티티(도메인)에 두면 좋은 이유**가 여기서 드러납니다. DB도, 스프링도 없이 가장 빠르고 확실하게 테스트할 수 있어요.
{: .prompt-tip }

### ② Service 테스트: Mockito로 가짜 넣기
`MemberService`는 `MemberRepository`가 필요합니다. 진짜 DB 대신 **원하는 대로 동작하는 가짜(Mock)** 를 넣으면 Service 로직만 떼어서 볼 수 있어요. 6편에서 말한 **생성자 주입 덕분에 가능한 일**입니다.

```java
@ExtendWith(MockitoExtension.class)
class MemberServiceTest {

    @Mock
    MemberRepository memberRepository;     // 가짜 저장소

    @InjectMocks
    MemberService memberService;           // 가짜를 생성자로 주입받은 진짜 Service

    @Test
    @DisplayName("없는 회원을 조회하면 MemberNotFoundException이 발생한다")
    void findMember_notFound() {
        // given: findById(999L)를 부르면 빈 Optional을 돌려줘라
        given(memberRepository.findById(999L)).willReturn(Optional.empty());

        // when & then
        assertThatThrownBy(() -> memberService.findMember(999L))
                .isInstanceOf(MemberNotFoundException.class);
    }
}
```

* **`@Mock`**: 껍데기만 있는 가짜 객체 생성. 아무 설정 없으면 `null`, 빈 값 등을 돌려줍니다.
* **`given(...).willReturn(...)`**: "이렇게 호출하면 이걸 돌려줘라" 하고 **각본을 정함** (BDDMockito)
* **`@InjectMocks`**: `@Mock`들을 생성자에 넣어서 테스트 대상 객체를 만듦
* **`verify(memberRepository).save(any())`**: 특정 메서드가 **호출됐는지** 검증할 때 사용

> Mock은 강력하지만 **너무 많이 쓰면** "가짜끼리 잘 맞물리는지"만 확인하는 테스트가 됩니다. 실제 쿼리가 맞는지, 트랜잭션이 걸리는지는 Mock으로 알 수 없어요. 그건 다음 장의 통합 테스트 몫입니다.
{: .prompt-warning }

## 🏗️ 5. 통합 테스트: `@SpringBootTest` ⭐⭐가장 중요
**통합 테스트**는 스프링 컨테이너를 **실제로 띄우고**, 진짜 빈과 진짜 DB를 연결해서 여러 계층이 함께 잘 동작하는지 확인합니다.

```java
@SpringBootTest
@Transactional
class MemberServiceIntegrationTest {

    @Autowired MemberService memberService;
    @Autowired MemberRepository memberRepository;

    @Test
    @DisplayName("저장한 회원을 조회할 수 있다")
    void findMember() {
        // given
        Member saved = memberRepository.save(new Member("홍길동", "hong@test.com"));

        // when
        MemberResponse response = memberService.findMember(saved.getId());

        // then
        assertThat(response.name()).isEqualTo("홍길동");
    }
}
```

* **`@SpringBootTest`**: 애플리케이션 전체를 띄워서 **모든 빈을 컨테이너에 등록**합니다.
* 테스트 클래스는 생성자 주입 대신 **`@Autowired` 필드 주입**을 써도 괜찮습니다. 테스트는 다른 곳에서 주입받아 쓸 일이 없으니까요.

### 🔙 `@Transactional`을 붙이면 자동 롤백
4편에서 `@Transactional`은 예외가 없으면 **커밋**한다고 했죠. 그런데 **테스트에 붙으면 동작이 다릅니다.** 테스트가 끝나면 성공·실패와 상관없이 **항상 롤백**해요.

```text
테스트 시작 → 트랜잭션 시작
  → 회원 저장, 조회, 검증
  → 테스트 종료 → 롤백! (DB는 테스트 전 상태 그대로)
```

덕분에 테스트끼리 데이터가 섞이지 않고, 몇 번을 돌려도 **같은 결과**가 나옵니다. "이메일 중복" 테스트가 앞 테스트에서 저장한 회원 때문에 엉뚱하게 실패하는 일이 없죠.

> **함정 하나:** 롤백되는 테스트에서는 저장한 엔티티가 **영속성 컨텍스트(2편)에만 있고 실제 INSERT가 안 나갈 수도** 있습니다. DB 제약 조건이나 실제 쿼리까지 확인하고 싶다면 중간에 `em.flush()`로 SQL을 강제로 보내고, `em.clear()`로 1차 캐시를 비운 뒤 다시 조회하세요.
{: .prompt-warning }

> **`@Commit` / `@Rollback(false)`** 를 붙이면 롤백하지 않고 커밋합니다. 데이터를 직접 눈으로 보고 싶을 때만 잠깐 쓰세요.
{: .prompt-info }

## 🔪 6. 슬라이스 테스트: 필요한 계층만 잘라서
`@SpringBootTest`는 확실하지만 **모든 빈을 띄우니 느립니다.** 특정 계층만 확인하고 싶다면 그 계층에 필요한 빈만 올리는 **슬라이스 테스트**를 씁니다.

### `@DataJpaTest`: Repository만
```java
@DataJpaTest
class MemberRepositoryTest {

    @Autowired MemberRepository memberRepository;

    @Test
    void findByEmail() {
        memberRepository.save(new Member("홍길동", "hong@test.com"));

        Optional<Member> found = memberRepository.findByEmail("hong@test.com");

        assertThat(found).isPresent();
    }
}
```
JPA 관련 빈만 올리고, **`@Transactional`이 기본으로 포함**되어 있어 테스트마다 롤백됩니다. 직접 만든 쿼리 메서드가 맞게 동작하는지 확인할 때 좋아요.

### `@WebMvcTest`: Controller만
5편에서 공들여 만든 **에러 응답 형식**을 검증해 볼게요. Controller와 `@RestControllerAdvice` 같은 **웹 계층 빈만** 올리고, Service는 가짜로 대신합니다.

```java
@WebMvcTest(MemberController.class)
class MemberControllerTest {

    @Autowired MockMvc mockMvc;

    @MockitoBean   // Spring Boot 3.4 이전에는 @MockBean
    MemberService memberService;

    @Test
    @DisplayName("없는 회원 조회 시 404와 M001 코드를 응답한다")
    void getMember_notFound() throws Exception {
        given(memberService.findMember(999L)).willThrow(new MemberNotFoundException());

        mockMvc.perform(get("/members/999"))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.code").value("M001"))
                .andExpect(jsonPath("$.message").value("회원을 찾을 수 없습니다."));
    }

    @Test
    @DisplayName("이름이 비어 있으면 400과 필드 에러를 응답한다")
    void join_invalid() throws Exception {
        String body = """
                { "name": "", "email": "not-an-email" }
                """;

        mockMvc.perform(post("/members")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(body))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.code").value("C001"))
                .andExpect(jsonPath("$.errors.length()").value(2));
    }
}
```

* **`MockMvc`**: 서버를 실제로 띄우지 않고 **가짜 HTTP 요청**을 DispatcherServlet(1편)에 흘려보내는 도구
* **`jsonPath("$.code")`**: 응답 JSON에서 원하는 값을 꺼내 검증
* **`@MockitoBean`**: 컨테이너 안의 빈을 **Mock으로 바꿔치기**. 4장의 `@Mock`은 스프링과 무관한 가짜고, 이건 **스프링 빈으로 등록되는** 가짜예요.

> `@Valid` 검증은 Service까지 가지 않고 Controller 입구에서 막히기 때문에(5편), 두 번째 테스트는 Service Mock에 아무 각본이 없어도 400이 나옵니다. 이런 게 바로 **"내 설계대로 동작하는지"를 코드로 증명**하는 순간이에요.
{: .prompt-tip }

## 🔺 7. 무엇을 얼마나 테스트할까?
### 테스트 피라미드
```text
          /\
         /  \     E2E / 통합 테스트  — 적게 (느리지만 실제와 가장 비슷)
        /----\
       /      \   슬라이스 테스트    — 적당히
      /--------\
     /          \ 단위 테스트        — 많이 (빠르고 원인 파악이 쉬움)
    /____________\
```

**빠른 단위 테스트를 넓은 바닥으로 깔고**, 느린 통합 테스트는 핵심 흐름 위주로 위에 얹는 구조가 이상적입니다.

### 좋은 테스트의 조건 (FIRST)
| 원칙 | 의미 |
| --- | --- |
| **F**ast | 빨라야 자주 돌린다 |
| **I**ndependent | 테스트끼리 순서·데이터에 의존하지 않는다 (→ 롤백!) |
| **R**epeatable | 언제 어디서 돌려도 같은 결과 |
| **S**elf-validating | 성공/실패를 사람이 판단하지 않고 코드가 판단 (`println` ❌) |
| **T**imely | 기능을 만들 때 함께 작성한다 |

> **테스트 이름에 의도를 적으세요.** `test1()`보다 `@DisplayName("잔액보다 많이 출금하면 예외가 발생한다")`가 훨씬 낫습니다. 테스트는 **"이 코드가 어떻게 동작해야 하는가"를 적은 살아 있는 문서**이기도 해요.
{: .prompt-tip }

## 🧭 8. 한 장으로 정리
| 테스트 종류 | 도구 | 무엇을 확인? | 속도 |
| --- | --- | --- | --- |
| 단위 (도메인) | JUnit5 + AssertJ | 엔티티의 비즈니스 규칙 | ⚡⚡⚡ |
| 단위 (Service) | Mockito `@Mock`, `@InjectMocks` | Service 로직 흐름 | ⚡⚡⚡ |
| Repository 슬라이스 | `@DataJpaTest` | 쿼리, 매핑 | ⚡⚡ |
| Controller 슬라이스 | `@WebMvcTest` + `MockMvc` | 요청/응답, 검증, 에러 형식 | ⚡⚡ |
| 통합 | `@SpringBootTest` + `@Transactional` | 계층 전체 협력, 트랜잭션 | ⚡ |
