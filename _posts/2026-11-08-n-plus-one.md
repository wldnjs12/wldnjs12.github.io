## 👋 3편에서 미뤄둔 숙제
3편에서 **N+1 문제**를 맛보기로만 다루고 "나중에 깊게 정리하겠다"고 했습니다. 이제 그 숙제를 할 차례입니다.

이번 글에서는 N+1이 **언제, 왜** 생기는지 다시 짚고, **페치 조인 · `@EntityGraph` · 배치 사이즈** 세 가지 해결책을 비교합니다. 그리고 지난 글에서 배운 **테스트 코드로 쿼리 수가 실제로 줄어드는지** 증명해 볼게요.

---

## 🔍 1. 먼저 쿼리를 눈으로 보자
N+1은 **에러가 나지 않습니다.** 결과도 정확하게 나와요. 그래서 쿼리 로그를 보지 않으면 **존재 자체를 모르고 지나치기 쉽습니다.** 개발할 때는 항상 SQL 로그를 켜 두세요.

```yaml
# application.yml
spring:
  jpa:
    properties:
      hibernate:
        format_sql: true        # SQL 줄바꿈해서 보기 좋게

logging:
  level:
    org.hibernate.SQL: debug                 # 실행되는 SQL
    org.hibernate.orm.jdbc.bind: trace       # ? 에 들어가는 파라미터 값
```

> `spring.jpa.show-sql: true`도 SQL을 보여주지만 `System.out`으로 찍혀서 로그 파일에 남지 않습니다. **로거(`logging.level`)로 설정하는 쪽**을 권장해요.
{: .prompt-tip }

### 다시 보는 N+1
3편의 회원(N) - 팀(1) 관계, 모든 연관관계는 `LAZY`입니다.

```java
List<Member> members = memberRepository.findAll();
List<String> teamNames = members.stream()
        .map(m -> m.getTeam().getName())    // 프록시 초기화 → 쿼리!
        .toList();
```

```sql
select m.* from member m;                 -- 1번: 회원 N명 조회
select t.* from team t where t.id = ?;    -- 회원1의 팀
select t.* from team t where t.id = ?;    -- 회원2의 팀
...                                       -- 최대 N번
```

**핵심은 `LAZY`든 `EAGER`든 N+1은 생긴다는 것**입니다. `LAZY`는 **팀에 접근하는 순간** 나눠서, `EAGER`는 **조회 직후 곧바로** 나눠서 나갈 뿐이에요(3편). 로딩 전략은 "언제" 가져올지를 정할 뿐, **"한 번에" 가져오라는 지시가 아닙니다.**

> 식당으로 치면 **주문 10개를 받고 손님마다 창고에 한 번씩 다녀오는 것**입니다. 해결책은 결국 **"창고 갈 때 한 번에 다 가져와"** 라고 알려주는 거예요.
{: .prompt-info }

## 🚀 2. 페치 조인(fetch join) ⭐⭐가장 중요
JPQL에서 **`join fetch`** 를 쓰면 연관된 엔티티를 **SQL JOIN 한 번으로 같이 조회해서 영속성 컨텍스트에 채워 넣습니다.**

```java
public interface MemberRepository extends JpaRepository<Member, Long> {

    @Query("select m from Member m join fetch m.team")
    List<Member> findAllWithTeam();
}
```

```sql
select m.*, t.*
from member m
join team t on t.id = m.team_id;    -- 단 1번!
```

이제 `m.getTeam()`에는 프록시가 아니라 **이미 채워진 진짜 `Team`** 이 들어 있어서, `getName()`을 불러도 추가 쿼리가 나가지 않습니다. 트랜잭션 밖에서 접근해도 `LazyInitializationException`이 나지 않아요.

### 일반 join과 무엇이 다를까?
```java
@Query("select m from Member m join m.team t where t.name = :name")
List<Member> findByTeamName(String name);
```

```sql
select m.*                    -- 회원 컬럼만!
from member m
join team t on t.id = m.team_id
where t.name = ?;
```

* **일반 join:** 조인은 하지만 `SELECT`에는 **회원만** 담습니다. 팀은 **조건 거는 용도**로만 쓰이고, `m.getTeam()`은 여전히 프록시 → **N+1 그대로**
* **fetch join:** `SELECT`에 **팀 컬럼까지** 담아서 엔티티를 채웁니다 → **N+1 해결**

> "조인했는데 왜 쿼리가 또 나가지?" 하는 경우는 대부분 `join`과 `join fetch`를 헷갈린 것입니다. **같이 쓸 데이터면 `fetch`까지** 적어야 해요.
{: .prompt-warning }

## 💥 3. 컬렉션 페치 조인의 함정
이번엔 반대 방향, **팀(1) → 회원들(N)** 을 페치 조인해 볼게요.

```java
@Query("select t from Team t join fetch t.members")
List<Team> findAllWithMembers();
```

### ① 데이터 뻥튀기
DB 입장에서 1:N 조인은 **N쪽 개수만큼 행이 늘어납니다.**

| team.id | team.name | member.name |
| --- | --- | --- |
| 1 | 백엔드팀 | 지원 |
| 1 | 백엔드팀 | 철수 |
| 2 | 프론트팀 | 영희 |

팀은 2개인데 결과 행은 3개죠. 예전 Hibernate 5에서는 이 때문에 **같은 팀이 중복으로** 담겨서 JPQL에 `distinct`를 꼭 붙여야 했습니다. **Spring Boot 3(Hibernate 6)부터는 엔티티 중복을 자동으로 제거**해 줘서 `distinct` 없이도 팀 2개가 나옵니다. 다만 **DB에서 가져오는 행 수 자체는 여전히 많다**는 건 기억해 두세요.

### ② 페이징이 메모리에서 일어난다 🚨
컬렉션 페치 조인에 페이징을 걸면 문제가 커집니다.

```java
@Query("select t from Team t join fetch t.members")
Page<Team> findAllWithMembers(Pageable pageable);   // ❌
```

"팀 10개만"을 SQL `LIMIT`으로 자르면 **회원 행 기준으로 잘려서** 팀의 회원 목록이 중간에 끊겨 버립니다. 그래서 Hibernate는 **`LIMIT` 없이 전부 가져온 다음 메모리에서 페이징**하고, 이런 경고를 남겨요.

```text
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
```

팀이 10만 개라면 10만 개(와 그 회원 전부)를 메모리에 올립니다. 운영 서버가 **OutOfMemory로 죽을 수 있는** 위험한 코드예요.

> 경고만 띄우고 넘어가는 게 불안하다면 `spring.jpa.properties.hibernate.query.fail_on_pagination_over_collection_fetch: true`로 설정해 **아예 예외가 나게** 만들 수 있습니다. 실수를 개발 단계에서 잡아낼 수 있어요.
{: .prompt-tip }

### ③ 컬렉션은 하나만
`List`로 된 컬렉션 두 개를 동시에 페치 조인하면 `MultipleBagFetchException`이 발생합니다. 억지로 된다 해도 행이 **곱하기로** 불어나요. **컬렉션 페치 조인은 한 번에 하나만** 쓴다고 생각하세요.

**정리하면, 페치 조인은 `@ManyToOne`·`@OneToOne`(ToOne) 쪽에는 마음껏, `@OneToMany`(ToMany) 쪽에는 신중하게.** 그럼 ToMany는 어떻게 할까요? 5장의 배치 사이즈가 답입니다.

## 🏷️ 4. `@EntityGraph`: 어노테이션으로 하는 페치 조인
JPQL을 쓰기 귀찮거나, Spring Data JPA의 **메서드 이름 쿼리**에 페치 조인을 얹고 싶을 때 씁니다.

```java
public interface MemberRepository extends JpaRepository<Member, Long> {

    @EntityGraph(attributePaths = {"team"})
    List<Member> findAll();               // 기본 메서드도 오버라이드 가능

    @EntityGraph(attributePaths = {"team"})
    List<Member> findByName(String name); // 메서드 이름 쿼리 + 팀 같이 조회
}
```

내부적으로는 페치 조인과 같은 원리지만, SQL이 **`left outer join`** 으로 나간다는 차이가 있습니다. 그래서 팀이 없는 회원도 결과에 포함돼요. (`join fetch`는 기본이 inner join이라 팀 없는 회원은 빠집니다.)

## 📦 5. 배치 사이즈: N+1을 1+1로
배치 사이즈는 접근 방식이 다릅니다. 조인으로 한 번에 가져오는 게 아니라, **지연 로딩이 일어날 때 하나씩 말고 여러 개를 `IN` 절로 묶어서** 가져오게 합니다.

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

설정 한 줄이면 끝입니다. 이제 팀 목록과 회원들을 조회하면:

```java
List<Team> teams = teamRepository.findAll();         // 팀 조회
teams.forEach(t -> t.getMembers().size());           // 회원 접근
```

```sql
select t.* from team t;                                     -- 1번
select m.* from member m where m.team_id in (?, ?, ?, ...); -- 1번 (최대 100개씩)
```

**1 + N이 1 + 1**이 됐습니다. (팀이 250개라면 100, 100, 50으로 나눠서 1 + 3번)

### 왜 컬렉션에 딱 좋을까?
* 팀 조회 쿼리에는 조인이 없으니 **행이 뻥튀기되지 않고**
* 그래서 팀 조회에 **페이징(`LIMIT`)을 정상적으로** 걸 수 있습니다.
* 컬렉션이 여러 개여도 각각 `IN` 쿼리로 가져오니 **`MultipleBagFetchException`도 없어요.**

```java
Page<Team> page = teamRepository.findAll(PageRequest.of(0, 10));  // ✅ LIMIT 10
// 이후 members 접근 시 IN 쿼리 1번
```

> 특정 연관관계에만 적용하고 싶다면 필드나 클래스에 **`@BatchSize(size = 100)`** 을 붙이면 됩니다. 크기는 보통 **100~1000** 사이로 잡는데, DB가 `IN` 절 파라미터 수를 제한하는 경우도 있으니 너무 크게 잡지는 마세요.
{: .prompt-info }

## 🗺️ 6. 그래서 무엇을 쓸까?
| 상황 | 추천 방법 |
| --- | --- |
| **ToOne** (`@ManyToOne`, `@OneToOne`) 같이 조회 | **페치 조인** (페이징도 OK, 행 안 늘어남) |
| 메서드 이름 쿼리에 ToOne 얹기 | **`@EntityGraph`** |
| **ToMany** (`@OneToMany`) 같이 조회 | **`default_batch_fetch_size`** |
| ToMany + 페이징 | ToOne은 페치 조인, ToMany는 **배치 사이즈** |
| 그래도 느리다 / 필요한 컬럼만 원한다 | **DTO로 직접 조회** (`select new ...Dto(...)`) |

실무 공식처럼 쓰이는 조합은 이렇습니다.

1. 모든 연관관계는 **`LAZY`** (3편)
2. `default_batch_fetch_size`는 **기본으로 켜 둔다** (안전망)
3. 화면에서 같이 쓰는 **ToOne은 페치 조인**으로 가져온다
4. 그래도 부족하면 그때 DTO 직접 조회를 고민한다

> 배치 사이즈를 켜 두면 **"페치 조인을 깜빡해도 1+N이 1+1 수준으로"** 완화됩니다. 그래서 거의 모든 프로젝트에서 기본으로 설정해 두는 편이에요.
{: .prompt-tip }

## 🧪 7. 테스트로 쿼리 수 증명하기
"N+1이 해결됐다"를 눈으로 로그 세는 대신 **코드로 검증**해 봅시다. Hibernate의 **통계(Statistics)** 기능을 켜면 실행된 쿼리 수를 셀 수 있어요.

```java
@DataJpaTest(properties = "spring.jpa.properties.hibernate.generate_statistics=true")
class MemberRepositoryQueryCountTest {

    @Autowired MemberRepository memberRepository;
    @Autowired TeamRepository teamRepository;
    @Autowired EntityManager em;

    Statistics statistics;

    @BeforeEach
    void setUp() {
        for (int i = 1; i <= 5; i++) {
            Team team = teamRepository.save(new Team("팀" + i));
            memberRepository.save(new Member("회원" + i, team));
        }
        em.flush();    // INSERT를 DB로 보내고
        em.clear();    // 1차 캐시를 비워서 진짜 조회가 일어나게 (7편)

        statistics = em.getEntityManagerFactory()
                .unwrap(SessionFactory.class)
                .getStatistics();
        statistics.clear();   // 준비 과정의 쿼리는 세지 않기
    }

    @Test
    @DisplayName("findAll은 N+1이 발생한다")
    void findAll_nPlusOne() {
        List<Member> members = memberRepository.findAll();
        members.forEach(m -> m.getTeam().getName());

        assertThat(statistics.getPrepareStatementCount()).isEqualTo(1 + 5);
    }

    @Test
    @DisplayName("fetch join은 쿼리 1번으로 회원과 팀을 조회한다")
    void findAllWithTeam() {
        List<Member> members = memberRepository.findAllWithTeam();
        members.forEach(m -> m.getTeam().getName());

        assertThat(statistics.getPrepareStatementCount()).isEqualTo(1);
    }
}
```

* **`em.clear()`가 핵심**입니다. 빼먹으면 `setUp`에서 저장한 팀이 1차 캐시에 남아 있어서, 지연 로딩이 DB까지 가지 않고 **N+1이 재현조차 안 됩니다.** 7편에서 말한 함정이 여기서 그대로 나와요.
* `getPrepareStatementCount()`는 **실행 준비된 SQL 수**, 즉 DB에 보낸 쿼리 수입니다.

> 이런 테스트를 남겨 두면, 나중에 누군가 `findAllWithTeam()`의 `fetch`를 실수로 지워도 **테스트가 바로 빨간불**을 켜 줍니다. 성능도 회귀 테스트의 대상이에요.
{: .prompt-tip }

## 🧭 8. 한 장으로 정리
| 개념 | 한 줄 정리 |
| --- | --- |
| N+1 | 1번 조회한 N개의 결과마다 연관 엔티티 조회 쿼리가 추가로 나가는 문제 |
| 원인 | 로딩 전략(LAZY/EAGER)은 "언제"만 정할 뿐, "한 번에"를 지시하지 않음 |
| 발견 | `org.hibernate.SQL: debug`로 **SQL 로그를 항상 확인** |
| 페치 조인 | `join fetch`로 연관 엔티티까지 **SQL 1번에** 조회 |
| 일반 join vs fetch join | 일반 join은 조건용, **SELECT에 안 담김** |
| 컬렉션 페치 조인 | 행 뻥튀기, **페이징 시 메모리 페이징**, 컬렉션은 하나만 |
| `@EntityGraph` | 어노테이션 페치 조인, **left outer join** |
| 배치 사이즈 | `IN` 절로 묶어서 **1+N → 1+1**, 컬렉션·페이징에 적합 |
